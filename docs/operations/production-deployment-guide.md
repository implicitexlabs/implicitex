# ImplicitEx Production Deployment Guide — hosting:main

**Status:** Interim repository-enforced guard active.
**Final control:** CI-only deployment (not yet implemented — see §Roadmap).

---

## Why this document exists

On 2026-07-31, an older git worktree (`implicitex-change-001r`, branch
`integration/wp-02-canonical-reconciliation`) was accidentally deployed to
production. That worktree was 133 commits behind the active branch. It had no
predeploy hooks in its `firebase.json`, so no validation ran. The deployment
silently replaced the live site with a version missing the settlement
screenshots, how-it-works section, two-row header, and Tourmaline palette.

See: `docs/operations/incidents/2026-07-31-production-recovery.md`

The **root cause is structural**: every worktree that contains a `.firebaserc`
and a `firebase.json` can execute `firebase deploy --project production` and
overwrite the live site. Cleaning up stale worktrees reduces the attack surface;
it does not eliminate it. The interim guard in this document adds a required
authorization step before any `hosting:main` deployment can proceed.

---

## Why `build-info.json` is not authorization

`build-info.json` is generated by `scripts/generate_build_info.js` during the
**portal** deploy (`predeploy:portal`). It writes the current `git rev-parse HEAD`
to `app-web/frontend/public/build-info.json` and causes the live portal to
display a short commit hash in its UI.

This is **observability**, not authorization. It answers: *what was deployed?*
It does not answer: *was this deployment authorized?* A wrong-worktree deploy
would faithfully publish that worktree's (stale) SHA in `build-info.json`.
The displayed SHA would be wrong, but by the time you read it, the deployment
has already overwritten the production site.

For `hosting:main`, `build-info.json` is explicitly **absent** (404 from the CDN).
The production guard checks for its presence as a separate condition (check 11).
If it exists at deploy time, the guard fails — it means the portal predeploy ran,
which is the wrong preparation for a `hosting:main` deploy.

**Design rule:** a displayed commit SHA tells you what happened after the event.
Deployment authorization determines what is permitted to happen before the event.
They are different systems and must not be conflated.

---

## Repository root resolution

The guard derives its repository root exclusively from the process working
directory, using `git rev-parse --show-toplevel`. There is no environment
variable, hidden argument, or alternate mechanism to redirect validation to a
different directory. The guard always validates the repository the operator is
actually working in.

## Production deployment — permitted workflow

### Prerequisites

1. You are deploying from an **immutable SHA**, not a branch name.
   Verify: `git rev-parse HEAD` returns a 40-character hex SHA.

2. The worktree is **clean**:
   ```
   git status --short --untracked-files=all
   ```
   Output must be empty. No tracked modifications, staged files, or untracked
   non-ignored files.

3. `build-info.json` does **not** exist in the public directory:
   ```
   ls app-web/frontend/public/build-info.json
   ```
   Expected: `No such file or directory`. This file is gitignored and therefore
   invisible to `git status`. The guard checks for it separately.

4. You have **independently reviewed** the public directory and accept its
   contents as the intended production artifact.

### Step 1 — Generate the manifest

```
npm --prefix app-web run manifest:main -- --output /tmp/implicitex-manifest-$(git rev-parse --short HEAD).json
```

This walks `app-web/frontend/public/`, computes a SHA-256 for every file, and
writes a structured JSON manifest. The manifest contains a `manifest_hash` field:
the SHA-256 of the sorted `path:sha256:bytes` lines. This scalar independently
identifies the entire artifact tree, binding both content and file sizes.

The generator fails immediately on symlinks, FIFOs, sockets, or device nodes in
the public directory — these are never silently omitted from the manifest.

**Review the manifest before proceeding.** Verify that file names, counts, hashes,
and byte counts match your expectation. The manifest is your authorization token.

### Step 2 — Deploy

The guard runs **twice** through the wrapper workflow:

1. **Early check (wrapper):** The `deploy:main` script invokes the guard directly
   before starting Firebase. This catches authorization failures immediately,
   without Firebase initializing at all.

2. **Final check (Firebase predeploy):** The guard is the last hook in
   `firebase.json`'s `hosting:main` predeploy array. It runs after all tests,
   generators, and deterministic publication steps have completed. This is the
   authoritative check: the approved manifest is compared to the actual artifact
   tree that Firebase is about to upload.

```
IMPLICITEX_PRODUCTION_MODE=true \
IMPLICITEX_APPROVED_SHA="$(git rev-parse HEAD)" \
IMPLICITEX_APPROVED_MANIFEST_PATH="/tmp/implicitex-manifest-$(git rev-parse --short HEAD).json" \
firebase deploy --only hosting:main --project production
```

Or using the npm wrapper (equivalent — runs early guard then Firebase):

```
IMPLICITEX_PRODUCTION_MODE=true \
IMPLICITEX_APPROVED_SHA="$(git rev-parse HEAD)" \
IMPLICITEX_APPROVED_MANIFEST_PATH="/tmp/implicitex-manifest-$(git rev-parse --short HEAD).json" \
npm --prefix app-web run deploy:main
```

If any check fails, the deployment does not proceed.

### Step 3 — Verify post-deployment

```
curl -s -I https://implicitex.com | grep -E "HTTP|Cache-Control|X-Cache"
curl -s https://implicitex.com | sha256sum
```

The SHA-256 of the live `index.html` must match the SHA-256 in your manifest
for `index.html`.

## What the guard checks

The guard (`scripts/production_deploy_guard.js`) runs all 12 checks in sequence.
Any failure is fatal; the guard exits 1 and prints a specific reason.

| # | Check | Variable / source |
|---|---|---|
| 1 | `IMPLICITEX_PRODUCTION_MODE === 'true'` | Environment |
| 2 | `IMPLICITEX_APPROVED_SHA` is 40 lowercase hex chars | Environment |
| 3 | `IMPLICITEX_APPROVED_MANIFEST_PATH` is readable JSON | Environment + filesystem |
| 4 | Manifest structurally valid: schema_version, manifest_hash, non-empty files | Manifest |
| 4b | `manifest.commit` is 40-char hex and equals `IMPLICITEX_APPROVED_SHA` | Manifest + environment |
| 4c | `manifest.public_dir` equals `app-web/frontend/public` | Manifest |
| 4d | `manifest.file_count` is a non-negative integer equal to `files.length` | Manifest |
| 4e | No absolute paths, no `../` traversal, no backslash per entry | Manifest |
| 4f | Valid 64-char lowercase hex sha256 per entry | Manifest |
| 4g | Non-negative integer bytes per entry | Manifest |
| 4h | No duplicate paths | Manifest |
| 5 | `git rev-parse HEAD` matches approved SHA | Git |
| 6 | `git status --porcelain` is empty | Git |
| 7 | `.firebaserc` `production` alias resolves to `implicitex` | `.firebaserc` |
| 8 | `firebase.json` `hosting:main` public is `app-web/frontend/public` | `firebase.json` |
| 9 | Public directory contains no symlinks or special files | Filesystem |
| 10 | Every file matches manifest by SHA-256 and byte count | Filesystem |
| 11 | `build-info.json` absent unless explicitly in approved manifest | Filesystem |
| 12 | Re-derived manifest hash matches approved value | Filesystem + manifest |

The manifest hash (check 12) is SHA-256 of the sorted `path:sha256:bytes` lines,
so it covers file identity, content, and size in a single scalar.

On pass, the guard prints a concise approval record: absolute path, commit SHA,
project, target, public directory, artifact file count, and manifest hash.

## firebase.json predeploy order

```json
"predeploy": [
  "npm --prefix app-web run predeploy:coin-card",
  "node docs/blockaid-review-packet/build-public-page.js",
  "git diff --exit-code app-web/frontend/public/architecture-and-security.html",
  "npm --prefix app-web run guard:production"
]
```

The guard is **last**. This ensures it verifies the artifact tree after:
- The Coin Card release gate has validated runtime modules
- `build-public-page.js` has written the Blockaid page into `public/`
- The architecture-and-security diff check has confirmed no uncommitted changes

If the guard ran first, subsequent hooks could modify the artifact tree after
approval. Running last makes the comparison authoritative.

## Bypass paths — residual risk

**Repository enforcement is not the final security boundary.**

The following bypass paths remain as long as local Firebase production credentials
are available:

1. **Worktree on a branch predating this guard:** `implicitex-codex-cc0023`
   (`coincard/cc-002.3-registry-state`) currently diverges from this branch and
   has the pre-guard `firebase.json`. A `firebase deploy --only hosting:main
   --project production` from that worktree bypasses the guard entirely. **Production
   deployment is frozen until both active worktrees contain the guard.**

2. **Any pre-guard checkout:** Any branch, stash, or archived worktree that
   predates this commit has no guard hook. A `firebase deploy` from there runs
   the 3 original content checks only.

3. **Direct `firebase deploy` from the guarded worktree:** If an operator sets
   the three required env vars, they can invoke `firebase deploy` directly (without
   the npm wrapper). The guard still runs as the final predeploy hook — this is
   correct. The npm wrapper provides an ergonomic early-fail; the predeploy hook
   is the security control.

4. **Local Firebase production credentials:** Any operator with a live
   `firebase login` session can deploy from any worktree with `.firebaserc`. No
   IAM control prevents this at the account level.

## Roadmap: CI-only production deployment

The interim guard must eventually be replaced by CI enforcement. Required controls:

1. **Firebase service account with deploy-only permissions**
   — Scoped to `implicitex` project, hosting only.
   — Key stored in CI secrets, never on local machines.

2. **Protected production environment in CI**
   — Manual approval gate required before any production deploy.
   — No automated trigger on merge.

3. **Signed tag or approved commit as the authorization token**
   — PGP-signed tag or approved-commit SHA from a protected branch.
   — Branch names are mutable; SHA or tag is the authority.

4. **Local production deploy permanently disabled**
   — After CI deployment is live, revoke local Firebase credentials for the
     production project.
   — `firebase deploy --project production` from any local environment becomes
     unauthorized at the IAM level.

5. **Audit log**
   — Every production deployment emits: who, from what SHA, at what time, with
     what manifest hash.

Until CI deployment is available, the repository guard is the primary control.
Use it without exception.

## Running the tests

```
npm --prefix app-web run test:production-guard
```

36 test cases. Tests run in isolated temporary git repositories. They never
contact Firebase, never read the production public directory, and never perform
any deployment.

Guard coverage (30 tests): correct credentials (PASS), wrong SHA, missing SHA,
wrong mode, dirty tracked file, staged file, untracked file, wrong Firebase
project, wrong public dir, missing main target, gitignored artifact modified
after approval, stale `build-info.json`, absent manifest, missing manifest path,
malformed JSON, wrong schema version, empty files array, tampered manifest hash,
absent file on disk, symlink in public directory, `../` path traversal, absolute
path in manifest, duplicate manifest path, wrong byte count,
`IMPLICITEX_GUARD_REPO_ROOT` ignored, firebase.json configuration verification,
manifest commit differs from approved SHA, invalid manifest commit format, wrong
manifest public_dir, and manifest file_count mismatch.

Generator coverage (6 tests): produces valid manifest from a clean temporary git
repository, emits the current full commit SHA, emits the correct public directory
and file count, computes the same canonical `path:sha256:bytes` manifest hash as
the guard, refuses a dirty working tree, and refuses a symlink in the public
directory.
