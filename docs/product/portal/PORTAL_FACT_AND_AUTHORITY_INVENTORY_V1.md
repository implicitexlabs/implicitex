# Portal Fact and Authority Inventory V1

Implementation baseline: `d72532c`

This inventory describes the committed portal implementation at the baseline above. The current worktree also contains unrelated uncommitted runtime and test changes. Those pending changes are excluded from this baseline and are not treated as current authority here.

## 1. Purpose

This document inventories facts currently displayed by the portal implementation and records their present producer, authoritative owner, renderer, persistence owner, authority class, volatility, preservation rule, current render locations, intended IA destination, and interruption class.

It examines the committed implementation baseline. It does not define new navigation or move any portal surface.

## 3. Authority conflicts and duplicated presentation sources

- Recipient facts appear in several places today: transfer form, preview, Coin Card intake, recipient intel, and receipt history. The source of authority depends on the kind of fact: user intent, Coin Card route evidence, or browser-local history.
- Wallet and network facts are duplicated across the sender row, wallet menu, network badge, contract panel, preview, companion, and telemetry. The live provider plus configured chain data own the truth; the render targets are projections.
- Fee and total facts are rendered in the transfer form, preview, and companion guidance. The shared execution fee calculation in `ix-execution.js` is the baseline formula; `wallet.js` renders and uses the returned values. No committed-baseline duplicate fee formula was found.
- Receipt facts are duplicated across the receipt store, verification panel, companion, and receipt history. Execution output and chain evidence create the truth; `receipt-store.js` preserves browser-local copies.
- Telemetry is a secondary projection of wallet and transfer state. It is useful for diagnosis and support, but it does not own the underlying facts.
- Installation state is owned by browser capability and the portal shell, not by transaction logic.

## 4. Ambiguities to resolve before navigation work

- The current portal does not yet have dedicated Recipients or Activity destinations. Those concepts are represented today by in-place widgets, local recipient storage, and receipt history.
- Coin Card route evidence, Coin Card lifecycle evidence, and display labels are distinct. A verified route does not make a label a verified identity claim.
- The local recipient book and local receipt archive are browser-local only. They are convenience persistence, not a server-side customer database.
- Some facts are intentionally duplicated for user safety, especially network, fee, total, and receipt evidence. Those duplicates are projections until a future navigation project chooses a single presentation path.
- Uncommitted runtime work remains outside this baseline and is not treated as current authority.
- This inventory does not decide the future destination layout. It only records where the committed implementation already puts the facts.
